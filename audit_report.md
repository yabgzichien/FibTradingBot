# Codebase Audit Report

## 1. Strategy Logic ([strategy.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py))
- **Lookahead Bias:** The strategy logic ([generate_signals_refined](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py#112-362)) appropriately uses `.shift(1)` for HTF anchor context and for dynamic internal structure calculations, effectively avoiding lookahead bias.
- **Invalidation Logic Missing:** In [generate_signals_refined](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py#112-362), once a sweep is found and the strategy actively waits for a BOS (Break of Structure), there is no check to see if the price breaks the sweep low (for longs) or sweep high (for shorts) before the BOS occurs. If the sweep extreme is breached, the current active setup should ideally be invalidated, as the market structure has failed in that localized instance. Currently, it will just keep waiting for the BOS level to be broken up to `max_bos_wait_bars` away, even if the price has dumped below the original sweep.

## 3. Backtesting Logic ([backtest.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/backtest.py))
- **Limit Order Execution Constraints**: When executing a pending order in backtesting, [backtest.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/backtest.py) correctly processes spread and slippage cost metrics. It evaluates both SL and TP in the entry bar as controlled by `allow_entry_bar_tp` and `both_hit_policy`.
- **Missed SL Fill Condition**: If slippage/spread makes `entry_cost_points` significant, the backtest adds it to `pending_entry`. If a gap occurs where the open of the candle is below `pending_entry` (for longs), `row['low'] <= pending_entry` will still trigger. However, realistic limit order executions in a gap should fill at the open price, not `pending_entry`.

## 4. Live Trading & EA Bridge ([ea_bridge.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py) & [AntigravityBridgeEA.mq5](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea/AntigravityBridgeEA.mq5))
- **CRITICAL BACKTEST VS LIVE DIVERGENCE**: In [strategy.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py), the `setup_id`, `entry_level`, and associated signal columns are only set directly on the EXACT `idx[i]` candle where the Break of Structure (BOS) occurs. It is **not** forward-filled. 
    - In [backtest.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/backtest.py), this is fine because it internally caches `pending = True` upon seeing the signal and waits for the retracement up to `max_pending_bars`.
    - BUT in [ea_bridge.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py), [_latest_setup](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py#166-178) simply checks `df.iloc[-2]`. If `setup_id` is missing (which will happen on the very next 15-minute candle after the BOS candle since it's not forward-filled), it returns `None`. When `setup_setup is None`, [ea_bridge.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py) immediately queues a `CANCEL_ALL` command.
    - **RESULT**: The MQL5 EA will cancel your pending limit order 15 minutes after it places it. Unless the price perfectly retraces to your 61.8% entry within the exact 15-minute candle right after the BOS, your trades will never trigger in live trading!
- **State Persistence Risk**: The [AntigravityBridgeEA.mq5](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea/AntigravityBridgeEA.mq5) completely ignores the `max_pending_bars` string argument passed via the CSV command. If [ea_bridge.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py) crashes and restarts, it might lose track and re-send the limit order over an already actively running market position, as it only looks at the `ag_commands.csv` for `_has_equivalent_pending`.
- **Active Position Tracking**: The python bridge ([ea_bridge.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/ea_bridge.py)) does not verify with MT5 if the pending limit order has already been triggered into a live position before canceling or replacing.

## 5. Additional Issue (Strategy)
- **Setup Invalidation Logic**: In [strategy.py](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py) inside [generate_signals_refined](file:///c:/Users/yang/Desktop/xmum/my-own/antigravity_test_trading_bot/trading_bot/strategy.py#112-362), while waiting for a BOS from a swept low (or swept high), there is no check if the price invalidates the original sweep by dropping even lower before breaking structure. Wait-limits like `max_bos_wait_bars` don't guard against structure invalidation during the wait.
